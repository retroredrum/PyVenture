# 05 — Multilingue (i18n)

## 1. Objectifs

- Jouer au même jeu en français, anglais, puis toute autre langue.
- Traduire **le contenu** (pièces, objets, messages, fins) et **l'interface** (menus, boutons, erreurs du moteur).
- Ajouter une langue sans modifier le code.
- Détecter les traductions manquantes avant de livrer.
- Garder le parser utilisable dans chaque langue.

## 2. Deux niveaux de traduction

### 2.1 Contenu du jeu

Les textes du jeu sont localisés dans `game.yaml` :

```yaml
description:
  fr: |
    Vous êtes dans une chambre poussiéreuse.
  en: |
    You are in a dusty bedroom.
```

Règles :

- Une chaîne simple = identique dans toutes les langues.
- Un objet = une entrée par langue.
- La langue par défaut sert de fallback.
- Les IDs et les clés de messages ne sont **jamais** traduits.

### 2.2 Interface et moteur

Les chaînes de l'interface et du moteur sont dans des catalogues séparés :

```text
pyventure/locales/
├── ui.fr.yaml
└── ui.en.yaml
```

```yaml
# ui.fr.yaml
menu.file: Fichier
menu.save: Sauvegarder
command.unknown_verb: "Je ne comprends pas « {verb} »."
parser.ambiguous: "Plusieurs objets correspondent à « {name} ». Précisez."
game.saved: "Partie sauvegardée."
```

- Même format que les messages du jeu : clé → texte.
- Le moteur utilise un `Translator` avec fallback.
- Les placeholders sont validés (mêmes clés dans toutes les langues).
- Les catalogues peuvent être exportés en CSV/PO pour des traducteurs.

## 3. Langue courante

- Ordre de priorité : `--lang` en CLI → préférence utilisateur → `meta.default_language`.
- Changement à chaud : commande `language en` ou menu « Langue ».
- Le changement réaffiche la pièce courante, l'inventaire et l'interface, sans perdre l'état.
- La langue est sauvegardée dans la sauvegarde de partie.
- Les codes sont BCP-47 (`fr`, `en`, `pt-BR`, `zh-Hant`).

## 4. Fallback

```text
langue demandée
      |
      v
texte dans cette langue ?
      | oui -> afficher
      | non
      v
langue par défaut
      |
      v
texte dans la langue par défaut ?
      | oui -> afficher + warning
      | non
      v
première langue disponible
      |
      v
clé brute + warning (mode strict : erreur)
```

En développement, un mode `--strict-i18n` transforme les manques en erreurs. En production, on affiche un fallback et on logge.

## 5. Parser multilingue

Le vocabulaire est déclaré par langue dans `game.yaml` :

```yaml
vocabulary:
  verbs:
    fr:
      prendre: get
      ramasser: get
      regarder: look
      examiner: look
      utiliser: use
    en:
      get: get
      take: get
      look: look
      examine: look
      use: use
  directions:
    fr: {nord: n, sud: s, est: e, ouest: w}
    en: {north: n, south: s, east: e, west: w}
```

- Les valeurs (`get`, `look`, `n`) sont canoniques et indépendantes de la langue.
- Les clés sont les mots réellement tapés.
- Les synonymes d'objets sont aussi par langue.
- Les articles sont ignorés par le parser, avec une liste par langue.
- Les accents sont normalisés pour la comparaison (`clé` = `cle`).
- Les verbes multi-mots sont supportés (`pick up`).

## 6. Genre, pluriel et grammaire

Le MVP reste simple : les textes sont des chaînes avec placeholders.

```yaml
messages:
  take_item:
    fr: "Vous prenez {article} {object}."
    en: "You take {object}."
```

Plus tard, si nécessaire :

```yaml
grammar:
  fr:
    flashlight: {gender: f, article: "la"}
    knife: {gender: m, article: "le"}
```

- Le moteur pourra fournir `{article}` et accorder les participes.
- Pour le pluriel, préférer des messages distincts (`one`/`other`) plutôt qu'un moteur ICU complet au départ.
- Ne pas sur-ingénierer : la majorité des textes d'aventure sont des phrases complètes.

## 7. Workflow de traduction

1. L'auteur écrit la langue par défaut.
2. L'éditeur affiche les colonnes par langue et surligne les manques.
3. Un traducteur remplit les cellules ou importe un CSV.
4. La validation vérifie :
   - clés manquantes ;
   - placeholders incohérents ;
   - textes vides ;
   - longueur excessive (avertissement UI).
5. L'aperçu permet de jouer dans la langue cible.
6. Le mode pseudo-locale (`[!! texte !!]`) teste les débordements.

## 8. Ajouter une langue : checklist

- [ ] Ajouter le code dans `languages`.
- [ ] Traduire `meta.title` et les textes de toutes les pièces.
- [ ] Traduire les objets, messages et fins.
- [ ] Ajouter le vocabulaire (verbes, directions, prépositions, synonymes).
- [ ] Créer `pyventure/locales/ui.<lang>.yaml`.
- [ ] Vérifier les placeholders.
- [ ] Lancer le jeu avec `--lang <code>` et `--strict-i18n`.
- [ ] Vérifier l'affichage (accents, longueur, police).
- [ ] Mettre à jour la documentation joueur.

## 9. Formats et encodage

- UTF-8 partout (fichiers, terminal, pygame).
- YAML avec `ruamel.yaml` pour préserver les commentaires.
- Pas de texte codé en dur dans le code : tout passe par les catalogues ou le contenu.
- Les noms de fichiers restent en ASCII (slugs).
- Les polices doivent couvrir les langues cibles ; prévoir une police de secours.

## 10. Tests i18n

- Charger le projet dans chaque langue : aucune exception, aucun fallback silencieux en mode strict.
- Vérifier que tous les messages ont les mêmes placeholders.
- Golden transcripts par langue.
- Test du changement de langue en cours de partie.
- Test du fallback quand une traduction manque.
- Test du parser avec accents, articles et synonymes.

## 11. Décisions

- **Pas de gettext au départ** : les catalogues YAML sont plus simples à éditer et à intégrer dans l'éditeur.
- **Pas d'ICU au départ** : chaînes + placeholders suffisent ; on ajoutera le genre/pluriel si le contenu l'exige.
- **Une seule source de vérité** : le contenu dans `game.yaml`, l'UI dans `locales/`.
- **La langue est une donnée de partie**, pas une constante globale.
